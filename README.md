# Buderus RC30 Schedule — v0.5.1

Home Assistant custom integration for the **HC1, own 1** switching schedule
through **EMS-ESP32 3.9.1**. The dashboard supports local drafts and explicit,
verified saves of the **42 physical slots (00–41)**. It never changes the selected
program, temperatures or operating modes.

The owner has confirmed the read integration and weekly dashboard on a live
installation. The new write/restore flow is covered by automated tests with
synthetic data; it still requires its first controlled live acceptance check.
No live gateway is contacted during development or automated testing.

## Requirements

- Home Assistant **2026.10 or newer**; automated integration tests target 2026.10.4
  on Python 3.14. Older Home Assistant versions are not supported by this release.
- EMS-ESP32 **3.9.1**, exposing `/api/thermostat/hc1/switchtime1` and
  `/api/thermostat/hc1/program`. Other firmware versions have not been verified.
- An EMS-ESP API key authorized to execute the selector POST. In 3.9.1 this may
  require write/command permission for both reading selectors and saving slots.
- Network access from Home Assistant to the gateway.

## Install with Marketplace (formerly HACS)

The repository is public and can be added as a **custom integration repository**:

1. Open **Marketplace → three-dot menu → Custom repositories**.
2. Add `https://github.com/jaal2001/ha-buderus-rc30` with type **Integration**.
3. Download **Buderus RC30 Schedule** and restart Home Assistant.
4. For a new installation, open **Settings → Devices & services → Add integration
   → Buderus RC30 Schedule** and enter the hostname and API key. Existing config
   entries remain configured when upgrading or switching from a manual install.
5. Allow up to three minutes for initial schedule validation.
6. Reload the browser. The bundled card is registered automatically in v0.4.1+;
   no dashboard resource URL needs to be added or maintained.

Marketplace manages subsequent downloads/updates using numbered GitHub releases. Restart Home Assistant and reload the
browser after an update. Without releases, HACS uses the default branch; a change
available only in an unmerged PR is not installed from `main` yet.

For a manual installation, download the successful CI artifact or repository,
copy `custom_components/buderus_rc30` to `/config/custom_components/buderus_rc30`,
and restart Home Assistant. Do not nest an extra `custom_components` directory.

Credentials are stored in Home Assistant's config entry storage. The password
field masks the key but does not encrypt Home Assistant backups. Protect those
backups. No credentials, local hostnames or real schedule fixtures belong in Git.
Use HTTP only on a trusted local network, or HTTPS with a trusted certificate.
TLS verification is enabled; redirects are rejected.

## Sensors

| Sensor | State / attributes |
| --- | --- |
| Occupied schedule slots | Occupied count; `slots` attribute contains all 42 entries |
| Free schedule slots | `42 - occupied_count` |
| Active program | Current program reported by HC1 |
| Last verified poll | UTC timestamp of the last complete successful pass |

Names follow the Home Assistant interface language (English and German included).
Entity IDs are generated by Home Assistant; use the entity selector instead of
assuming a fixed ID. All sensors belong to one device.

The schedule sensor includes `heating_circuit`, `schedule_program`, `active_program`,
`capacity`, `free_slots`, `verified_at`, `slots` and local `save_status` metadata. Each slot has `slot` (two-digit
physical index), `occupied`, `day`, `time` and `mode`. Empty slots use `null` for
day/time/mode. The schedule always describes **own 1**, even if the active program
is something else. It must not be interpreted as the active heating schedule in
that case. Counts are calculated; 38 occupied slots are an example, not a constant.

Example attribute entry (synthetic):

```json
{"slot": "01", "occupied": true, "day": "mo", "time": "09:30", "mode": "off"}
```

## Live weekly dashboard card

The integration now includes `custom:buderus-rc30-schedule-card`. It shows seven
daily timelines, heating/setback intervals, occupied/free slot counts, the active
program and the timestamp of the last complete poll. Click a day timeline to open its day editor
with exact heating time ranges. The card uses the existing sensor attributes;
reading the overview causes no gateway requests. Only explicit Save/restore actions
use authenticated Home Assistant WebSocket commands carrying entity IDs and slots,
without gateway hostnames or API keys. Progress queries read local state only.

### Upgrade and automatic card registration (v0.4.1+)

1. Update the integration through Marketplace and restart Home Assistant. Existing
   gateways, credentials, sensors and dashboard cards remain configured.
2. Fully reload the browser. The integration registers its bundled JavaScript
   module using Home Assistant's frontend API and the installed manifest version.
   The URL version changes automatically on upgrades to avoid stale browser caches.
3. Add **Buderus RC30 Wochenprogramm** in the dashboard card picker, or retain your
   existing card. Its complete minimal configuration is:

   ```yaml
   type: custom:buderus-rc30-schedule-card
   ```

The card detects exactly one matching sensor automatically. With multiple gateways,
select the intended sensor in the visual card editor or set `entity` to its actual
entity ID. The optional `title` changes the heading.

Automatic registration works in both storage and YAML resource modes. It is a
frontend module, so it does not need a manual entry in the dashboard **Resources**
list. Old manual storage entries for this integration's exact local card path are
removed to avoid loading multiple versioned URLs. Other resources and all YAML
configuration files remain unchanged. Existing YAML resource entries may remain,
but are no longer required for this card.

If **Custom element not found** appears after upgrading, check that the integration
is loaded, restart Home Assistant, then fully reload the browser. Also check the
Home Assistant log for frontend/dependency setup errors. No file needs to be copied
into `/config/www`, and no resource URL needs to be maintained manually.

### Interpretation and display limits

- Orange indicates the schedule's `on` mode; the background indicates `off`.
  These are programmed heating/setback periods, **not burner activity**.
- Times are interpreted as a repeating seven-day program, with state carried
  through midnight and across Sunday/Monday. `24:00` is the following midnight.
  Empty slots create no extra transitions. An entirely empty schedule displays
  a message instead of inventing a heating mode.
- The current-day/time marker and poll timestamp use Home Assistant's configured
  timezone, including DST. The marker assumes the thermostat clock uses the same
  local timezone. Stored switching times are wall-clock values and are not shifted.
  The current-time line remains visible in today's row while editing a draft;
  the draft label still identifies the displayed periods as unsaved changes.
- If another program is active, a warning identifies it while the card continues
  to show **own 1**. It does not infer the heating periods of another program.
- Unavailable or invalid sensor data hides the timelines. Data older than 30
  minutes displays a prominent warning and no current-time marker.
- No external JavaScript, fonts or frameworks are downloaded. The card follows
  the Home Assistant theme, supports keyboard activation of weekday details and
  has a maximum width of 600 px. The owner confirmed the v0.2 overview visually;
  the new write/restore controls still need a live dashboard check.

## Day dialog, Apply and Save

Click an existing horizontal day timeline to open that day's editor. The weekly
layout is retained. The editor shows only the selected day's heating/setback
ranges, a small day timeline and the current clock-time line. Day tabs let you
move through the week; a dot identifies days with applied, unsaved changes.

- Click an orange range or its row to edit **Von** / **Bis** directly in that row.
  **Apply** confirms both boundaries together into the local draft. Times use
  ten-minute increments and allow an end of `24:00`.
- Click a setback row or **+ Heizzeit** to prepare a new heating range. Overlaps
  are rejected; touching heating ranges merge. At most 42 physical switch slots
  may be occupied, including any midnight boundaries required by the edit.
- **− Heizzeit** prepares removal of a range and also requires **Apply**.
  **Rückgängig** restores up to 42 recent draft actions. An unchanged Apply creates
  no additional undo entry.
- Applied changes retain the selected day and dialog scroll position. **Wochenvorschau**
  closes the dialog while preserving the applied draft for inspection in the
  original week view. Clicking another day opens its editor.
- **Cancel**, the close button and Escape warn before discarding pending input
  or applied changes. Switching day/range also protects unconfirmed form input.
- **Save** transfers the entire applied weekly draft after a final confirmation.
  It is enabled only for Home Assistant administrators, with confirmed changes,
  valid source data and no unresolved recovery. Unapplied form input must first
  be applied or discarded. Apply and day navigation perform no gateway requests.
  An entirely empty program is rejected because its heating behavior is undefined.

Editing a day preserves the heating ranges of every other day. The draft updates
its necessary physical switching points and, when required, a midnight transition
that preserves the following day's original starting mode. A range crossing
midnight is shown as portions on its two days; edit those days separately.

Starting/editing requires valid, recent source data and active `own 1`. Unavailable
or stale source data pauses edits while retaining the draft. Source changes require
restarting the draft; a new poll timestamp with identical slots is accepted.
The existing non-atomic firmware snapshot limitation still applies.

Drafts exist only in the current card instance. They are not written to Home
Assistant storage or the gateway. Cancel provides an explicit in-card warning;
the card also requests the browser's standard unload warning, which a browser
may suppress and which Home Assistant navigation may not trigger. Card recreation,
page reload or navigation can discard the in-memory draft. It is not a backup.
The new Save/restore controls require live acceptance testing in the user's dashboard.

## Save availability (v0.5.1)

The overview badge reads **Wochenübersicht**, and changes to **Entwurf** while
editing. It does not indicate whether saving is authorized. The editor explains
why Save is unavailable: administrator permissions, backend status, unapplied
input, stale/changed source data, or pending recovery. A failed local status query
can be retried without querying the gateway. The visible card version helps
identify an old browser module after upgrades. Restart Home Assistant and reload
the browser after installing an update.

## Save and recovery (v0.5)

The normal Save path is deliberately limited to **one complete read before
writing, changed-slot writes, and one complete read afterward**:

1. Read all 42 slots and verify that `own 1` is still active and the slots match
   the draft baseline. A conflict stops the save before any mutation.
2. Atomically save the fallback and intended target in Home Assistant's private
   `.storage/buderus_rc30_save_<config_entry_id>` file before the first write.
   This journal contains schedule data and operation metadata, never credentials.
3. POST only changed physical slots using `NN day HH:MM on|off`, or `NN not_set`
   for a cleared slot. Slot numbers never shift; cleared slots are sent last.
   Commands are paced by 0.5 seconds, without additional verification requests
   for individual writes. A failed POST is never blindly retried.
4. Read all 42 slots again and compare the complete result and active program.
   A lost write acknowledgment can still succeed if the resulting program matches.
   Success requires the final full comparison; POST acknowledgment alone is insufficient.

Save/restore scans select a sentinel slot before the 42-slot pass, forcing a
cache identity change before slot `00`. The sentinel is not an additional full
scan. A successful Save with N changed slots normally uses **176 + N REST
requests**, versus 86 for an ordinary poll; mismatched read responses may require
bounded GET retries. Most requests are selectors/reads, not mutations.

If a write or final verification fails, the journal and draft remain available.
The card offers **Vorherigen Stand wiederherstellen …**, followed by a separate
**Ja, wiederherstellen** confirmation. There is **no automatic rollback**.
**Jetzt nicht** leaves the journal available for a later decision; new saves stay
blocked while recovery is unresolved. Before restoring, the integration reads
again and refuses to overwrite newer external changes. If the failed operation's
last result could not be read, each slot must still match either its original or
intended value. Restore writes only necessary differences and performs one final
complete verification. Restore can fail too; the fallback remains retained.

Only one save/restore runs per config entry, serialized with regular polling.
The frontend locks editing during an operation. A browser disconnect does not
cancel the Home Assistant background transaction; reconnecting queries local
status instead of repeating writes. An interrupted Home Assistant operation is
recognized from its persistent journal after restart and requires a decision.
Unloading the integration waits for an active operation to finish. Keep the
integration installed and connected until recovery is resolved.

A journal with invalid contents blocks writes rather than silently discarding
its fallback. Preserve that file and inspect the controller manually before
repairing storage. Only the latest journal is retained; this is not a schedule
backup history. Protect Home Assistant storage/backups because schedules can
reveal occupancy patterns.

The device has no atomic transaction or revision lock. Do not edit the controller
or query/write switchtimes from another script/client during a save or restore.
External edits during a scan cannot be ruled out completely. Gateway verification
is a full slot-identity/content comparison, not an independent physical readback
of burner activity.

## Polling and failure behavior

- One shared asynchronous coordinator refreshes every **15 minutes**.
- A poll reads the active program, then selects each slot sequentially with
  `POST /api/thermostat/hc1/switchtime1` and `{"value":"00"}` through
  `{"value":"41"}`. It then reads the same endpoint with GET. These two-character
  values enter the firmware's read branch; no schedule text is submitted.
- The client waits 0.5 seconds before each GET and accepts only a matching slot ID,
  recognized weekday, `on`/`off`, valid ten-minute time or `not_set`. `24:00` is
  accepted as an end-of-day time. Unsupported temperature modes such as `T2` fail
  explicitly instead of being converted.
- Cached responses for a different slot are retried at most six times. Each HTTP
  request has a five-second timeout; an entire pass is limited to three minutes.
  No partial schedule is published. A normal pass uses 86 requests, including
  the active-program checks before and after the slots.
- The program must match at both ends of the pass. Polls within one client cannot
  interleave. Other scripts or EMS-ESP clients must not query switchtimes at the
  same time. Host aliases are separate origins and must not be configured twice.
- Verification means format and slot-identity checks, **not an atomic hardware
  snapshot or proof of fresh bus data**. The firmware supplies no snapshot revision;
  changes made at the physical controller during a pass may still produce mixed
  data. The save/restore preflight and final comparison do not remove that firmware limitation.
- On failure, sensors become unavailable and the coordinator retains the previous
  good snapshot internally. The next successful pass restores availability.
  Initial communication failures retry via Home Assistant; authentication failures
  start reauthentication. An expired key can be replaced in the integration UI.
- For an occasional manual refresh, use Home Assistant's `homeassistant.update_entity`
  action on one sensor. Avoid repeatedly refreshing all four sensors.

## First live check

1. Stop any old switchtime polling script and install the integration.
2. Verify that all 42 slots, including `00` and `41`, appear in the attributes.
3. Compare occupied/free counts and several switching times with the controller.
   If the schedule has not changed since the original experiment, the counts should
   be 38 and 4. The active program was previously `own 1`.
4. Temporarily disconnect the gateway and confirm the entities become unavailable
   after a refresh, then restore connectivity and refresh once.
5. Confirm existing EMS-ESP entities and the heating dashboard still work.

No live gateway has been contacted by the automated tests. Do not post an API key
in issues or logs. Error messages deliberately omit response bodies and credentials.

## Development and packaging

```sh
python3.14 -m venv .venv
.venv/bin/python -m pip install -r requirements-test.txt
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/pytest -q --cov=custom_components.buderus_rc30 --cov-report=term-missing
deno test tests/frontend
.venv/bin/python scripts/package.py
```

The package command creates `dist/buderus_rc30.zip` containing only the integration
under `custom_components/buderus_rc30/`. GitHub Actions runs tests, lint, packaging
and hassfest, plus Deno tests for cyclic schedule interpretation. Test network
sockets are blocked; Unix sockets needed by the event
loop are allowed. The integration itself needs no additional pip requirements.
The HTTP test fixture supplies the new aiohttp 3.14 `stream_writer` constructor
argument that aioresponses 0.7.9 does not yet provide. This compatibility adapter
is test-only and leaves the production client and its validation unchanged.

Before broader Marketplace distribution: complete the live checks, choose a
license, validate with HACS and prepare versioned releases. The public repository
can already be used as a custom repository; no default-catalog submission or
GitHub release is created by this change.

## Removal

Delete the integration from **Settings → Devices & services**, remove
`/config/custom_components/buderus_rc30`, and restart Home Assistant. Revoke the
gateway API key if it was created solely for this integration.

## First write check

After upgrading to 0.5.0, restart Home Assistant and reload the browser. Use an
administrator account, change one heating boundary by ten minutes, Apply, inspect
the weekly draft, then Save and confirm. Wait for **Gespeichert und vollständig
geprüft** and compare that point directly with the controller. Changing it back
uses the same workflow. Do not deliberately disconnect the heater during this
first live check. The automatic module registration uses the manifest version to
refresh the bundled card.

The write interface is limited to `buderus_rc30/save`, `buderus_rc30/save_status`
and `buderus_rc30/restore` authenticated admin WebSocket commands. Entity registry
ownership, 42 unique physical slots, weekday/time/mode consistency and conflicting
switching points are checked independently by the backend. No generic REST proxy,
program/mode/temperature mutation or schedule-writing service is exposed.
