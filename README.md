# Buderus RC30 Schedule — v0.2.1

Read-only Home Assistant custom integration for the **HC1, own 1** switching schedule
through **EMS-ESP32 3.9.1**. It reads all **42 physical slots (00–41)** without
changing switching times, the selected program, temperatures or operating modes.

The v0.1 read integration has been installed successfully by the project owner:
all 42 slots and the expected occupied/free counts were confirmed. Version 0.2
adds the read-only weekly dashboard card. Its layout still needs verification
inside the user's Home Assistant. Automated tests use synthetic data, not a live
heating system.

## Requirements

- Home Assistant **2026.10 or newer**; automated integration tests target 2026.10.4
  on Python 3.14. Older Home Assistant versions are not supported by this release.
- EMS-ESP32 **3.9.1**, exposing `/api/thermostat/hc1/switchtime1` and
  `/api/thermostat/hc1/program`. Other firmware versions have not been verified.
- An EMS-ESP API key authorized to execute the selector POST. In 3.9.1 this may
  require write/command permission even though this integration only reads.
- Network access from Home Assistant to the gateway.

## Install while the repository is private

HACS does **not** support private repositories. This repository includes the
standard `custom_components` layout, manifest, local icon and `hacs.json` for
future public distribution, but it is not a published Marketplace integration.
The repository remains private.

1. Download the branch or the `buderus_rc30` artifact from a successful GitHub
   Actions run. The artifact contains `buderus_rc30.zip`; extract that ZIP.
2. Copy its `custom_components/buderus_rc30` directory to
   `/config/custom_components/buderus_rc30` in Home Assistant. Do not nest an
   extra `custom_components` directory inside the integration directory.
3. Restart Home Assistant.
4. Open **Settings → Devices & services → Add integration → Buderus RC30 Schedule**.
5. Enter the gateway hostname (for example `ems-esp.local`) or HTTP(S) origin
   (for example `http://ems-esp.local:8080`) and the API key. Do not include an
   `/api` path or credentials in the address.
6. Allow up to **three minutes** for the complete validation pass. Initial setup
   performs its own full pass before creating entities.

Credentials are stored in Home Assistant's config entry storage. The password
field masks the key but does not encrypt Home Assistant backups. Protect those
backups. No credentials, local hostnames or real schedule fixtures belong in Git.
Use HTTP only on a trusted local network, or HTTPS with a trusted certificate.
TLS verification is enabled; redirects are rejected.

## Sensors

| Sensor | State / attributes |
| --- | --- |
| Occupied schedule slots | Occupied count; `slots` attribute contains all 42 entries |
| Free schedule slots | `42 - occupied_count` |
| Active program | Current program reported by HC1 |
| Last verified poll | UTC timestamp of the last complete successful pass |

Names follow the Home Assistant interface language (English and German included).
Entity IDs are generated by Home Assistant; use the entity selector instead of
assuming a fixed ID. All sensors belong to one device.

The schedule sensor includes `heating_circuit`, `schedule_program`, `active_program`,
`capacity`, `free_slots`, `verified_at` and `slots`. Each slot has `slot` (two-digit
physical index), `occupied`, `day`, `time` and `mode`. Empty slots use `null` for
day/time/mode. The schedule always describes **own 1**, even if the active program
is something else. It must not be interpreted as the active heating schedule in
that case. Counts are calculated; 38 occupied slots are an example, not a constant.

Example attribute entry (synthetic):

```json
{"slot": "01", "occupied": true, "day": "mo", "time": "09:30", "mode": "off"}
```

## Live weekly dashboard card

The integration now includes `custom:buderus-rc30-schedule-card`. It shows seven
daily timelines, heating/setback intervals, occupied/free slot counts, the active
program and the timestamp of the last complete poll. Click a weekday to display
its exact heating time ranges. The card uses the existing sensor attributes;
it performs no API requests or service calls and cannot write switching times.

### Upgrade from v0.1 and add the card

1. Extract the v0.2 install ZIP and replace the existing
   `/config/custom_components/buderus_rc30` directory with its included directory.
   The new `www/buderus-rc30-schedule-card.js` file must be included. Existing
   config entries and API keys remain stored in Home Assistant.
2. Restart Home Assistant. Removing/re-adding the configured integration is not
   necessary. The integration serves the single JavaScript file itself; you do
   not need to copy files into `/config/www`.
3. Enable **Advanced mode** in your Home Assistant user profile if necessary.
   Open **Settings → Dashboards → three-dot menu → Resources → Add resource**.
4. Enter this URL and select **JavaScript module**:

   ```text
   /buderus_rc30/buderus-rc30-schedule-card.js?v=0.2.1
   ```

   For a YAML-managed resource list, use:

   ```yaml
   lovelace:
     resource_mode: yaml
     resources:
       - url: /buderus_rc30/buderus-rc30-schedule-card.js?v=0.2.1
         type: module
   ```

5. Reload the browser/dashboard. Edit the desired dashboard, choose **Add card**
   and select **Buderus RC30 Wochenprogramm**. The visual editor lets you choose
   the schedule sensor and an optional title. With exactly one schedule sensor,
   it is detected automatically. No entity-ID guess is needed.
6. Alternatively, add a **Manual** card with this complete configuration:

   ```yaml
   type: custom:buderus-rc30-schedule-card
   ```

   If multiple gateways are configured, select the intended sensor in the card
   editor or specify its actual entity ID using the `entity` setting. The
   optional `title` setting changes the heading.

If the card is not listed, confirm the resource is a JavaScript module, check the
URL for typos, and fully reload the browser. A 404 at the resource URL usually
means the integration files were not replaced completely or Home Assistant was
not restarted. Resource registration is manual; the integration does not change
your dashboard configuration.

### Interpretation and display limits

- Orange indicates the schedule's `on` mode; the background indicates `off`.
  These are programmed heating/setback periods, **not burner activity**.
- Times are interpreted as a repeating seven-day program, with state carried
  through midnight and across Sunday/Monday. `24:00` is the following midnight.
  Empty slots create no extra transitions. An entirely empty schedule displays
  a message instead of inventing a heating mode.
- The current-day/time marker and poll timestamp use Home Assistant's configured
  timezone, including DST. The marker assumes the thermostat clock uses the same
  local timezone. Stored switching times are wall-clock values and are not shifted.
- If another program is active, a warning identifies it while the card continues
  to show **own 1**. It does not infer the heating periods of another program.
- Unavailable or invalid sensor data hides the timelines. Data older than 30
  minutes displays a prominent warning and no current-time marker.
- No external JavaScript, fonts or frameworks are downloaded. The card follows
  the Home Assistant theme, supports keyboard activation of weekday details and
  has a maximum width of 600 px. A live dashboard visual check is still required.

## Polling and failure behavior

- One shared asynchronous coordinator refreshes every **15 minutes**.
- A poll reads the active program, then selects each slot sequentially with
  `POST /api/thermostat/hc1/switchtime1` and **only** `{"value":"00"}` through
  `{"value":"41"}`. It then reads the same endpoint with GET. These two-character
  values enter the firmware's read branch; no schedule text is submitted.
- The client waits 0.5 seconds before each GET and accepts only a matching slot ID,
  recognized weekday, `on`/`off`, valid ten-minute time or `not_set`. `24:00` is
  accepted as an end-of-day time. Unsupported temperature modes such as `T2` fail
  explicitly instead of being converted.
- Cached responses for a different slot are retried at most six times. Each HTTP
  request has a five-second timeout; an entire pass is limited to three minutes.
  No partial schedule is published. A normal pass uses 86 requests, including
  the active-program checks before and after the slots.
- The program must match at both ends of the pass. Polls within one client cannot
  interleave. Other scripts or EMS-ESP clients must not query switchtimes at the
  same time. Host aliases are separate origins and must not be configured twice.
- Verification means format and slot-identity checks, **not an atomic hardware
  snapshot or proof of fresh bus data**. The firmware supplies no snapshot revision;
  changes made at the physical controller during a pass may still produce mixed
  data. This version is unsuitable as a backup/restore source for later writes.
- On failure, sensors become unavailable and the coordinator retains the previous
  good snapshot internally. The next successful pass restores availability.
  Initial communication failures retry via Home Assistant; authentication failures
  start reauthentication. An expired key can be replaced in the integration UI.
- For an occasional manual refresh, use Home Assistant's `homeassistant.update_entity`
  action on one sensor. Avoid repeatedly refreshing all four sensors.

## First live check

1. Stop any old switchtime polling script and install the integration.
2. Verify that all 42 slots, including `00` and `41`, appear in the attributes.
3. Compare occupied/free counts and several switching times with the controller.
   If the schedule has not changed since the original experiment, the counts should
   be 38 and 4. The active program was previously `own 1`.
4. Temporarily disconnect the gateway and confirm the entities become unavailable
   after a refresh, then restore connectivity and refresh once.
5. Confirm existing EMS-ESP entities and the heating dashboard still work.

No live gateway has been contacted by the automated tests. Do not post an API key
in issues or logs. Error messages deliberately omit response bodies and credentials.

## Development and packaging

```sh
python3.14 -m venv .venv
.venv/bin/python -m pip install -r requirements-test.txt
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/pytest -q --cov=custom_components.buderus_rc30 --cov-report=term-missing
deno test tests/frontend
.venv/bin/python scripts/package.py
```

The package command creates `dist/buderus_rc30.zip` containing only the integration
under `custom_components/buderus_rc30/`. GitHub Actions runs tests, lint, packaging
and hassfest, plus Deno tests for cyclic schedule interpretation. Test network
sockets are blocked; Unix sockets needed by the event
loop are allowed. The integration itself needs no additional pip requirements.
The HTTP test fixture supplies the new aiohttp 3.14 `stream_writer` constructor
argument that aioresponses 0.7.9 does not yet provide. This compatibility adapter
is test-only and leaves the production client and its validation unchanged.

Before a future public Marketplace release: complete the live check, choose a
license, make a deliberate visibility decision, validate with HACS, and create a
versioned release. No public release or visibility change is performed by v0.2.

## Removal

Delete the integration from **Settings → Devices & services**, remove
`/config/custom_components/buderus_rc30`, and restart Home Assistant. Revoke the
gateway API key if it was created solely for this integration.

## Scope after v0.1

The read-only graphical weekly overview is included in v0.2. The graphical editor,
`+`/`−`, edit-capacity checks, change previews, backups and a separately designed
write/restore failsafe remain future work. This release has no schedule-writing
services or editing controls.
